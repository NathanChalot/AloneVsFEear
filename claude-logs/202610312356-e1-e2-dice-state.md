## Decisions

- **Mutable plain dataclasses**, changed only through `Game`. Rejected: event sourcing (replay and undo for free, but an event type and a fold for every change from day one).
- **History as counters**, not a log: per level, how many times each ID was played, found or killed, plus keywords. Every rule found that reads the past ("only once per game", "during this mission", "already defeated", "the first time") asks whether or how often, never when. The user first chose a log of records, then asked why; with no rule needing the "when", counters were kept.
- **A log file for debugging**, apart from the mechanics (the user's idea): standard `logging`, the engine only emits, the terminal interface (E4) will write it to a file.
- **Dice codes parsed from the printed notation.** Pros: same notation as the book and the YAML, content can hold "d6 Food" as text, tests copy the rules. Cons: a small parser, typos found at load time. Rejected: constructors only (the YAML strings would need mapping anyway), and waiting for D1.
- **Scripted dice for rule tests**, seeded dice for reproducibility. "x in 6" succeeds on x or less: a convention for scripted tests, the odds are the same.
- **E2 keeps the map to storage** (boxes by position, their numbers); geometry, sheets, moves and box memory are E3.
- **No clamping in E2**: losses can go below zero; what that means is a rule for E3, E5 and E13. `Game` refuses only what the state cannot hold (no character, unknown mission, negative amount, missing item).
- **GitHub issues only for user stories and bugs, only when needed** (the user). E1 and E2 have no user story, so no issue: an issue would only copy the Readme entry. The first candidate is E4.
- **The dice are not saved with the campaign**, and need not be: play should be random. Saving the dice state would only stop reloading to reroll (a solo player cheats only themself) or replay a game exactly for a bug (the log file covers most of that). Dropped from the open questions. For replay, E4 logs the seed and the player's answers (the user's idea): together they replay a game through the scripted interface, as long as the code has not changed.
- **Model review**: Opus at high effort fitted. The design questions were worth it (four API choices, one reversed after discussion); the code itself was straightforward. E3 stays on Sonnet, E4 on Opus high.

## Open questions

- What a loss bigger than what you have means: decided by the task that meets it, with the rules text in hand. E3 has the Food upkeep (its text already says what happens without Food); E5's manual actions raise the cases with no text (losing may stop at 0, while spending Clues or XP you do not have should be refused, to be asked); E13 has death and insanity. Clamping is a one-line change.
- History IDs are not checked against the content. Not an issue yet: only tests write records. From E10 on, a mistyped ID would make a gate silently answer "not played"; check IDs once creatures and events are in YAML.
