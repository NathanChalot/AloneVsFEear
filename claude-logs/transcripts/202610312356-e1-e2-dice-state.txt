⏺ Why keep a history at all

  Many rules ask about the past, so the game has to remember it. I found these
  in the rules text:

  - Once per game or campaign: each Special Event, each Unique Vampire, each
    book, each ritual, and the Dark clothes bonus.
  - Once per mission: Children's Stuff findings, event #9 at the farm, and some
    Arcane Skills.
  - Already defeated: Slashers are rerolled if you've beaten them, and Destroy
    the Coven counts the witches killed.
  - First time: Railways 4 gives 1 Clue the first time you find it.
  - Keywords: SNOWY, CLOWNFACE.

  Each level has its own history because each forgets at a different time. A new
  character loses what the old one knew, but the town still remembers which
  Slashers are dead.

  Why a log, though: I can't justify it. Every rule I found asks "has X
  happened?" or "how many times?". None asks when. The log's only advantage over
  counters is the box number, and nothing uses it. So I'd switch my
  recommendation to counters per kind plus a keyword set. That's smaller, and it
  covers every rule above. If a rule ever needs the "when", a counter can
  become a log without changing who calls it.

  Dice codes: pros and cons

  Pros
  Parse printed codes ("2d6+12"): Same notation as the book and the YAML (tables

  already say dice: 2d6). Content written later can say "d6 Food" or "3d6
  zombies" as plain strings. Tests read like the rules.
  Constructors only (nd6(2, plus=12)): No parser to write. The type checker
  catches mistakes.
  ────────────────────────────────────────
  Cons
  Parse printed codes ("2d6+12"): A small parser to write and test, about 30
  lines. A typo in a code only shows when content loads, not in the editor.
  Constructors only (nd6(2, plus=12)): The YAML strings still need turning into
  dice somewhere, which is a parser by another name. That leaves two ways to
  write the same thing.

  What decides it is how much the YAML will hold dice codes. Today that's only
  three table codes (d6, 2d6, d66). More, like "d6 Food", arrives only if D1
  puts amounts in YAML (E6). So there's a fair "not yet" option: constructors
  now, plus the three table codes, and a parser when D1 needs one.

  I'd still parse now. The parser is cheap, the book's notation is the spec, and
  it makes the dice tests a direct copy of the Dice Codes section. Your call.

  GitHub issues

  You're right: issues for E1 and E2 would only be following the Readme. Nobody
  else works on the repo, the Readme is the source of truth, and the PR and the
  session log already record the work. E1 and E2 are engine internals with no
  user story, since a player sees nothing yet. An issue would just copy the
  roadmap entry.

  Issues would earn their place for:

  - User stories, once there's something to play. The earliest are E4 ("a player
    walks 10 boxes") and E5 ("walks the town in book mode").
  - Bugs and rule misreadings found while playing.

  So I'd file no issues this session, and change the docs at wrap-up to match.
  That means WorkingWithClaude.md step 2, the Milestone 4 checkbox and the model
  table's "session issues" row: issues for user stories and bugs, only when
  needed.

  issues this session?

  Parallel sessions with a coordinator: my opinion

  Yes, but only for part of the remaining work, and the time saved is smaller 
  than it looks.

  Where it helps: the YAML batches, R2 to R7.
  - They don't depend on each other and don't touch the engine.
  - The existing tests check them: dice coverage, references, notes.
  - The prompt is already "copy, list doubtful readings, don't guess", so the
    work ends with questions rather than decisions. A coordinator handles that
    well: it dispatches 2–3 batch agents, each in its own worktree, collects
    their doubtful readings, asks you in one go, then opens the PRs.
  - That could turn the estimated 5–6 batch sessions into 1–2 coordinator
    sessions.

  Where it doesn't help: the engine tasks.
  - E3 through E20 form a chain. Only two pairs can run side by side: E8 with
    E9, and E15 alongside E12–E14. That chain is the critical path, roughly 15
    sessions, and parallel work barely shortens it.
  - Engine sessions are also where your design choices get made. Today there
    were four API choices, and one of them changed after you asked "why?". A
    subagent can't ask you directly. With a coordinator relaying, that
    back-and-forth gets slower and loses detail.

  Practical problems to settle before a pilot:
  - Shared files: every batch edits catalogue.yaml, the Readme and
    NextSession.md. Only the coordinator should edit those; the batch agents
    touch only their own YAML and Markdown files.
  - origin_rules/ is git-ignored, so a fresh worktree won't have the PDFs. The
    agents need the main checkout's absolute path.
  - Logs and transcripts: subagent transcripts can't be exported the way you
    export a session. The coordinator would write one log per batch from each
    agent's report.
  - Cost and review: each agent starts from scratch and re-reads the docs, so
    you save time but spend more. Reviewing several PRs and answering their
    questions becomes the real bottleneck.

  My suggestion: pilot it with one coordinator session running R2 and R3, the
  batches E6 needs. It can run at the same time as an interactive E3 or E4
  session. Overall that might save 4–5 of the ~25 sessions. That's worth having,
  but it doesn't change the shape of the plan.
