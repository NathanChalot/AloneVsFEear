  Goal (restated)

  The engine asks and the interface answers. The engine never reads input and
  never prints. The turn loop is: move, arrive, (Search), (free actions). It
  ends at death (Life 0), insanity (Sanity 0) or when the player quits. A
  scripted interface plays games in tests, and a minimal terminal shows the map,
  the character and the requests. Done when: a scripted test walks 10 boxes,
  and the terminal lets a player do the same.

  1. How the engine asks (the main choice)

  Later rules ask the player deep inside other steps: during a fight inside an
  event inside an arrival, and when choosing the order of reactions. The
  protocol has to make that cheap.

  A. Callback
  How it works: The engine holds an Interface. Any rule calls ask(request) and
  gets the answer back right away.
  For: Rule code reads like the book. Nested choices cost nothing. Simple to
  test.
  Against: Python's stack holds the game while a request waits, so saving
  happens
  only between turns. A later GUI or web app would run the engine in a thread
  (an adapter, not a rewrite).
  ────────────────────────────────────────
  B. Generators
  How it works: Every rule that may ask is a generator: it yields a request, and

  a driver sends the answer back.
  For: The engine stays passive and suits async UIs.
  Against: Contagious: every function on the path needs yield from, including
  the
  reaction chains. Easy to get wrong.
  ────────────────────────────────────────
  C. State machine
  How it works: The engine shows a pending() request, and answer(a) moves it on.
  For: It can save at any request.
  Against: Every multi-step rule (42 events, combat, reactions) has to be cut
  into explicit states. That costs a lot.

  I recommend A. "Saving = saving the campaign" already points to saving between
  turns.

  2. What goes over the protocol (recommendation)

  - ask(Request) -> answer: one generic Choose request with a topic (HOME,
    ACTION, MOVE… as an enum) and plain-data options (positions, action names).
    The interface uses the topic to decide how to show it; for example, a MOVE
    request shows the map. Other request shapes (a number, an order) get added
    when a task needs them.
  - The answer is always one of the options. The engine refuses anything else by
    raising GameError, so a bad scripted answer fails the test, and the
    terminal checks input before answering.
  - tell(Event): the engine reports what happened (arrived in box 7, ate 1 Food,
    starved, died), in order, as plain data. The interface narrates it. The log
    stays a debugging tool.
  - Layout: requests, events and the Interface protocol in engine/protocol.py,
    the loop in engine/loop.py. interface/scripted.py lives in the package
    rather than in tests/, because replay uses it. interface/terminal.py is the
    terminal, with an alone-against-fear console script.

  3. Log and replay (recommendation)

  - The terminal writes the log at DEBUG to logs/<date-time>.log, and I add
    logs/ to .gitignore.
  - RandomDice() with no seed picks a seed and logs it. Every answer is logged
    on a line the code can read back.
  - alone-against-fear --replay logs/x.log plays the logged answers back with
    the same seed, then hands over to the player at the point where the log
    stops. A test checks that seed + answers give the same final state.

  4. Settled by the rules, no ruling needed

  - Life reaching 0 means death; Sanity reaching 0 means insanity. Both are in
    the main rules. The loop checks after every step. What comes next (a new
    character, the campaign going on) is E13.
  - Search and the free actions are hook points in the loop, with nothing in
    them yet. E5 adds the manual Search roll and the Town Exploration roll on
    arrival.
