  What ruff does: it's a Python linter and formatter in one tool, and it's very
  fast.
  - ruff check . is the linter. It flags unused imports, undefined names, likely
    bugs (the B rules), unsorted imports (I) and outdated syntax (UP). The rule
    sets are chosen in pyproject.toml under [tool.ruff.lint].
  - ruff format . reformats code to a consistent style, like black does. Line
    length is set to 100.

  The CI workflow runs ruff check so style and obvious mistakes fail the PR.
  It's a common default, as the "pick common defaults" guideline says, and you
  can drop it or loosen the rules if it gets in the way.

  On TDD and BDD, here is my proposal. You decide the points marked as
  questions.

  TDD: the default for the engine. Red, green, refactor. For each task I write
  the tests from its "Done when" line first and show them failing, then
  implement, then tidy. It suits this project well: dice, map, combat and
  effects are pure logic with exact rules. The engine/interface split also makes
  everything testable without a terminal, because a scripted interface answers
  the engine's requests. Seeded dice make runs reproducible.

  BDD: for game behaviour, not for unit logic. Scenarios read like the rulebook:
  "Given a character with 2 Life, when the creature hits, then Life drops to
  1." They would be the executable form of your user stories. Two ways to do it:
  - Gherkin files with pytest-bdd: .feature files that you can read and edit
    without Python. This is closest to real BDD, and the stories you want on
    GitHub could be those scenarios. It adds a dependency and some ceremony.
  - Plain pytest in a given/when/then style: test names and comments that read
    as scenarios, with no extra tooling. It's lighter and easy to upgrade to
    Gherkin later.

  I'd lean towards plain pytest to start and move to Gherkin only if you want
  feature files as the shared spec. That matches "decide only what is worth
  deciding yet".

  Proposed split
  - Unit tests (TDD): dice, state, map, each rule in isolation.
  - Scenario tests (BDD): a scripted interface plays a short slice of the game,
    such as "walk 10 boxes" or "lose a fight, then get an Injury offer". Each
    issue/story maps to one or a few scenarios.
  - Rules coverage: a test per rule written from the Markdown, so a misreading
    shows up as a failing test.
