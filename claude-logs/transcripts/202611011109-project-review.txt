  Finding 1: rules that need to ask the player

  The callback protocol was chosen so that "a rule deep inside another asks the
  same way". In the code, nothing deep in the engine can ask:

  - Game changes all the state (engine/game.py), but it has only dice, content
    and campaign, no interface.
  - play() holds the interface (engine/loop.py:28), and the option check is the
    free function loop.ask (loop.py:56). Any other code could call interface.ask
    directly and skip the check.

  E5 will hit this first. mvp-scope says manual actions "go through the rules,
  exactly as written content would", for example losing Life offers an Injury.
  That means asking from inside a change to Life. If nobody decides where this
  goes, every later rule (E7–E14) will probably end up in Game, which is already
  240 lines covering the character, missions, map, clock, box memory and
  history.

  The options E5 would choose from:
  - (a) Game holds the interface and asks itself. Simplest, but Game becomes the
    home of every rule.
  - (b) Game stays a plain state writer. Rules that ask live in rule modules
    that get a small context: game, interface, and the checked ask. Book mode
    and later content call those modules.
  - (c) Pass the interface into every rule function. Noisy.

  My proposed action is to add "Decides: where rules that ask live" to E5 in the
  Readme, with these three options. I'd also note it as open in
  docs/architecture.md. I lean towards (b), but that's E5's call.

  Do you agree with the action, want to change it, or want to settle the
  question now?
