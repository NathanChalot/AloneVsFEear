⏺ I'd go with Python. Your plans for generative AI settle it.

  Why Python

  - Generative AI. Local LLMs (Ollama, llama.cpp, vLLM, transformers), image
    generation (diffusers, Stable Diffusion/Flux, ComfyUI, which is Python
    itself) and video generation (most open models ship Python first) all treat
    Python as their main language. Claude and other hosted APIs have SDKs
    everywhere, but local image and video generation is close to Python-only.
  - MVP speed. Python is already set up in the repo, and it's quick to write the
    hundreds of small special rules.
  - Typed state and the YAML schema. pydantic models give you typed game state
    and generate the schema used to check the YAML.

  How the others compare

  - TypeScript works fine with hosted APIs, but its local image and video
    options are much weaker. It wins only if a browser version becomes the
    priority.
  - Elixir (Nx, Bumblebee) is good at serving models and at running many things
    at once, but its model ecosystem is much smaller, and a solo turn-based game
    doesn't need its concurrency.
  - Ruby has thin AI libraries. It's better kept as the language you port to.

  Keeping a DragonRuby port possible

  DragonRuby runs on mruby, which has limited gem support, so the language
  matters less for a port than these four habits:

  1. All rules data stays in YAML. It's language-neutral, and it's most of the
     game's content.
  2. The engine stays plain: dataclasses or pydantic models plus functions, with
     no metaprogramming, so it maps line for line to Ruby.
  3. The AI features sit behind small interfaces in their own module, for
     example Narrator, Illustrator and an event narrator. The core game never
     depends on them, so a port or an offline game simply skips them.
  4. Dice and game state stay separate from the terminal interface.

  Is YAML the right choice?

  It's not clear yet. I picked a file format before looking at what the content
  actually is. The audit showed it's a mix of two things:
  - Plain data: creature stats (L4 Animal, Life 6, Damage 2), d6 and 2d6 tables
    that point to other tables, the weapon list.
  - One-off rules: "bullets bounce off on 1-2", "if you have dog food you may
    distract it", 42 branching events with choices, and states that persist
    (curses, fluid effects lasting 3 combats).

  YAML suits the first and is bad at the second. Pushing the one-off rules into
  YAML ends with a homemade rules language inside YAML, which is the usual way
  this kind of project goes wrong. YAML also has its own traps: implicit typing
  (no → false), indentation mistakes, and needing a separate schema to catch
  errors.

  These are the realistic options:

  Approach: YAML (or TOML) data + Python code for the special rules
  Strength: Portable data, easy to edit by hand
  Weakness: Each entry is split across two places
  ────────────────────────────────────────
  Approach: Content as Python (typed objects, special rules as small functions
  next to each entry)
  Strength: Everything in one place, type-checked, simplest for an MVP
  Weakness: Less separation from the engine; a port means translating the code
  (Python → Ruby is mechanical)
  ────────────────────────────────────────
  Approach: Markdown with frontmatter for events
  Strength: Narrative text stays readable
  Weakness: Same problem with the special rules

  My current guess is content as Python for the MVP, with the format revisited
  once real entries show what's purely data. That's still a guess, though, which
  is why I'd test it before deciding.
